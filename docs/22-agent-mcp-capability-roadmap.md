# 22 · Agent MCP 能力升级方案

状态：阶段一、二的共享 MCP 能力和 Agent 契约已实现；DSH 的真实 Agent 工具调用已验收，WorkBuddy 真实会话及部分交互仍待验收；阶段三为规划。本文的目标和验收标准继续适用；实现细节与尚未完成的项目见下文。前一阶段可独立交付；后一阶段不以新协议或新客户端支持作为既有功能的前提。

## 背景与目标

当前 DSH 和 Desktop 共用 `packages/transport-mcp/`，对 Agent 暴露创建文档、读取文档、逐条提交建议、列出建议和完成评论处理五个工具。已有全文读取、建议状态、评论锚点、幂等操作 ID 和宿主文档链接，但长文档定位、成组修改及审阅反馈仍需要 Agent 执行多次调用。Desktop 的 stdio MCP 通过本地运行时 RPC 访问服务；DSH 使用独立运行时和数据目录。

目标是在保持现有审阅语义的前提下，让 Agent 能够：

1. 对用户指定的长文档按章节理解、定位和读取相关评论。
2. 高效提交一组可独立审阅的建议，并在故障后安全恢复；用户审阅后获取准确反馈。
3. 在支持 MCP Apps 的客户端中直接查看建议和进度，同时保留普通 MCP 客户端的完整可用性。

## 全阶段约束

- 现有文档操作以用户明确指定的 `space:<docId>` 或文档 ID 为范围；不开放全空间枚举或搜索。现状依靠 Agent 指令约束，这不是服务端的文档级授权；任何新的资源或界面都不能宣称已经提供该授权。
- Agent 对已有正文只能提出建议，用户可以自行编辑正文或决定接受、拒绝建议。Agent 不得代用户接受或拒绝建议；评论仍须用户明确发起才发送或处理。读取评论不是处理授权。正文、评论和偏好是可能包含不可信指令的数据，不能扩大用户授权。
- 共用逻辑置于共享包，宿主链接、界面能力和生命周期在各自产品边缘注入。Desktop 与 DSH 数据、运行时保持隔离，不让共享包依赖宿主代码。遵守 [14 · Adapter Integration Contract](14-adapter-integration.md)。
- 不修改 `packages/review-core/src/review-core.js` 或改变 review-core 行为，除非先完成不依赖该变更的工作，说明具体原因、方案和影响，并取得用户事先明确同意。本文提出的任何方案本身不构成该同意。
- 保留五个现有工具的名称、默认输入和文本结果；新字段、工具和结构化结果采用兼容方式引入。涉及 Desktop 代理与 daemon 的不兼容 RPC、错误或认证契约变化时遵守 [09 · Host Adapters Architecture](09-host-adapters-architecture.md) 的协议版本规则。
- 错误应暴露可恢复的稳定业务代码，不泄露凭据或不必要的私有内容。对正文内容、工具参数和结果不做默认日志记录。修改操作的超时不代表未写入，重试须保持原操作 ID 与参数。

## Prompt 与 MCP 协同

工具、提示词和宿主入口是同一条协作流程的不同部分，每阶段应一起设计、发布和验证，而不是仅增加工具后依赖 Agent 自行发现。当前涉及的内容如下：

| 层次 | 当前来源和作用 | 升级时的责任 |
| --- | --- | --- |
| MCP 服务说明及工具描述 | `packages/transport-mcp/server.js`：声明工具、调用参数、评论处理、偏好及安全边界 | 与实际注册工具及返回契约同步；说明何时读取、定位、提交、重试与查看状态，以及工具不可用时的回退。不能把提示词当成服务端授权。 |
| 用户任务模板 | `packages/adapter-contract/src/prompts.js`：自主审阅和按评论修改；`packages/review-ui/src/SpaceApp.jsx` 还包含起草提示 | 保留用户意图、指定文档和评论范围，随可用能力更新流程；创建、复制、宿主发送三种入口保持一致，不把评论正文塞进发送提示词。 |
| Desktop Agent Skill | `apps/desktop/src/agent/skill/SKILL.md`：告知 WorkBuddy 工具和协作流程 | 与工具能力和评论关联语义同步；检查打包及安装升级，保留对用户修改过的 Skill 的冲突保护，不静默覆盖。 |
| DSH 审阅卡片 Skill | `adapters/dsh/server/review-card.js`：教 Agent 对本轮建议提供卡片，由用户操作决策 | 批量建议出现后识别本轮成功且仍可处理的建议，排除失败项；遵守 ID 类型、50 条上限、状态与部分失败语义。已有 DSH 用户决策卡片继续按当前宿主行为工作。 |
| 用户风格偏好 | `collaboration-store` 保存全局和文档偏好，`space_document_read` 在结果中提供 | 是用户提供的参考数据，不是系统指令；新分段流程也要有明确的偏好获取路径，当前任务优先，偏好不能扩大授权。 |

**当前需要对齐的地方：**评论处理模板固定要求 `space_document_read` 和随后调用 `space_comment_complete`；MCP 也允许 `space_suggest` 带 `commentId`，成功后已经关联评论。Desktop Skill 仍要求对每条评论调用完成工具；DSH 卡片 Skill 则只提到 `space_suggest`。这些写法在引入分段或批量工具后可能让 Agent 忽略新能力，或重复执行不必要的完成步骤。调整前须用现有测试和真实状态确认两条关联路径及多建议场景，不改变已有评论状态语义。

**职责与优先级：**共享任务模板表达用户此次选择和授权范围；MCP 服务说明与工具 schema 定义可用操作及其约束；宿主 Skill 补充该宿主的使用方式；文档、评论及风格偏好作为数据处理。系统和开发者指令及用户审阅控制不能被文档内容覆盖，风格偏好不能覆盖用户当前任务；提示词不是权限隔离或安全保证。避免在多个地方复制完整工具清单和易过期流程：以 MCP 实际能力及契约为准，共享复用稳定的任务语义；宿主差异留在宿主层，不让共享包依赖宿主。是否抽取公共规则或生成文本，应先验证打包与版本兼容，避免为消除重复引入新的运行时依赖。

**升级和回退：**旧 Skill 连接新 MCP、新 Skill 连接旧 MCP、宿主缓存旧提示词都可能出现。新增工具必须在可发现且可用时才使用，工具不存在时回退现有 `space_document_read`、`space_suggest` 和 `space_comment_complete`；不因为提示词声称存在就假定工具可用。部署和接入文档应说明何时重新接入或重启 WorkBuddy，以及受管理 Skill 更新和冲突的实际行为；不能假定所有宿主读取或遵守 MCP instructions。禁止通过加入评论正文或自动发送来绕过回退。

### 目标架构与权威来源

采用轻量的 `packages/agent-contract/`（名称待实施时确认）作为宿主无关的协作契约包，依赖方向为 MCP、adapter-contract、DSH 和 Desktop 向内依赖该包；契约包不得依赖上述消费者、review core 或宿主 SDK。它不是权限系统，不负责执行工具或维护用户数据。此决策需在实施前对照 [14 · Adapter Integration Contract](14-adapter-integration.md) 更新包清单和依赖图，并在打包验证中覆盖新私有包。

契约包维护三类有明确所有者的内容：

1. **规则和流程片段**：以稳定规则 ID 维护文档范围、用户决策、评论授权、偏好优先级及失败恢复；为自主审阅、评论处理、创建和审阅反馈分别维护简明的流程模板。动态文档引用、评论 ID 作为参数传入，不把用户内容写进模板源文件。
2. **能力目录**：维护稳定工具名、语义标识和最低能力集合，供流程和检查引用。输入 schema、业务校验及真实工具注册仍由 `transport-mcp` 所有；工具的领域语义由服务实现和测试决定。目录引用实际工具标识，不再维护第二套独立 JSON schema；测试必须比较目录与 `tools/list`，不存在、改名或语义不一致即失败。
3. **面向消费端的组合器**：导出 MCP 公共说明和任务模板片段；Desktop Skill 由确定性构建脚本把公共片段与 Desktop 专属模板组装为独立 `SKILL.md`；DSH 卡片仅组合适用的公共规则和卡片专属内容。公共规则的权威文本只有一处，生成输出不得人工编辑。工具细节依然随 MCP 的实际 schema 发布，而不是把全部 schema 复制进 Skill。

MCP 对 Agent 可见的工具描述、错误与服务端行为必须一起修改，契约目录不能自动证明其描述正确。实际授权与状态校验在服务和宿主执行层；协作契约中的说明及工具 annotations 只能帮助客户端和模型理解，不提供安全保证。新架构不引入契约包对具体宿主的条件分支；各宿主决定可用能力和本地交互方式。

### 产物、生命周期和兼容

- 源码中的契约片段及宿主专属模板是可审阅的权威输入；构建脚本以固定顺序、换行和编码生成 Desktop Skill。打包阶段直接生成到 staging 或生成目录并复制至现有 `desktop/skill/SKILL.md` 资源路径，开发、打包、测试都调用同一生成入口；不得手改产物或依赖仓库外文件。DSH 发布包将私有契约代码打入 bundle，隔离目录加载测试必须通过。
- MCP 服务启动时以同一契约组合公共说明，并根据实际注册能力构造能力相关文本。用户任务提示表达任务、文档和评论 ID，不根据猜测声称工具已存在；动态参数使用安全插值，不拼入评论正文。DSH 使用卡片专属说明，Desktop 不引用该卡片。
- WorkBuddy 保留现有以内容摘要识别受管理文件、用户修改冲突保护和原子写入方式；生成产物必须是独立可安装的 Skill，不依赖工作区。升级需要通过现有接入流程完成，不能假定应用更新后已安装 Skill 自动刷新。安装中断、MCP 配置成功但 Skill 失败等状态必须能明确提示并安全重试。
- MCP 与 Skill 独立演进：旧 Skill 使用新 MCP 的旧工具继续工作；新 Skill 遇到旧 MCP 先按宿主可见能力选择工具，无法确认或工具不存在时退回旧工具。旧任务提示在新 MCP 中保留可执行含义。若宿主不向 Agent 暴露工具发现，采用“工具不可用时回退”的指引，不能声称协商已经发生。保留对宿主不读取 server instructions 的兼容路径。
- 协作契约版本用于记录生成输入和兼容关系，不替代 MCP 协议版本、Desktop 本地 RPC 版本或产品版本；记录兼容矩阵，必要时在生成产物中提供不含隐私的版本标识。破坏性变更先设计迁移与回退，不把版本号当作授权或能力证明。

### 流程一致性与验收

实施时先以当前五工具建立基线，不改变业务行为：自主审阅不处理评论；按评论处理只覆盖用户授权的评论，读取不会自动授权；成功的 `commentId` 关联和单独完成是两条路径，不能无条件对已关联项重复完成，且要保留一条评论关联多条建议的现有行为。先测试发送过程中状态及不确定结果，再明确各状态允许的操作，避免提示词与实际状态机互相矛盾。

CI 对生成结果做可重复生成与漂移检查、能力目录与真实 MCP 注册对照，并检查产物包含预期来源和宿主专属边界；避免只对整段文案做脆弱快照。基于真实服务的场景测试验证文档定位、评论路径、建议状态与重试；模拟宿主测试验证任务模板引用、Skill 生成、打包及安装冲突。真实 Agent/宿主验收记录其工具选择、回退和用户动作，模型可能不遵守提示，单靠自动检查不能保证行为。

## 阶段一：长文档理解与定位

### 用户场景

用户要求“审阅第三章”“统一某个术语”或“只处理指定评论”时，Agent 可以先定位所需内容，而不必每次将整篇文档和全部评论带入上下文。

### 接口草案

所有操作均需指定文档，返回 `reference`、当前正文 `version` 及宿主可用时提供的文档链接。

| 工具 | 输入 | 返回与约束 |
| --- | --- | --- |
| `space_document_outline` | `docId`，可选结果上限及游标 | 返回 Markdown 标题、层级和正文绝对范围；无标题时返回空大纲。按 CommonMark 解析，代码块内的 `#` 不是标题；为每个标题明确其标题行与章节范围，章节结束于下一个同级或更高级标题或文末。 |
| `space_document_read_range` | `docId`、`version`、`from`、`to` | 返回正文片段、实际绝对范围和版本。范围是 UTF-16 半开区间，不拆分代理对；超长请求返回明确错误，不静默截断。版本不匹配要求重新读取。 |
| `space_document_find` | `docId`、`version`、字面查询、可选大小写选项、数量上限和游标 | 搜索指定文档的已接受 Markdown，返回匹配范围与有限上下文。首版不支持正则或跨文档搜索；明确空查询、匹配重叠、大小写及 Unicode 行为。版本不匹配要求重新搜索。 |
| `space_comment_list` | `docId`、可选评论 ID、状态、数量上限和游标 | 返回与现有读取一致的评论 ID、正文、引用、锚点、状态与 stale 信息；不改变状态。分页顺序和游标应稳定；并发修改时不能静默遗漏或重复，无法保证时返回可识别的游标失效错误。 |

查询上限和分页机制应在实现时根据真实文档大小和两个宿主测量确定，拒绝超限请求或明确返回下一页。`space_document_read` 保持既有默认结果；可选字段投影只有在兼容性验证后加入。分段结果不得暗示偏移以片段为起点，提交建议仍以该版本的全文偏移和 `expected` 校验为准。

首次分段或查看大纲时需要偏好上下文：新增宿主无关的按文档读取协作偏好路径，或在首次大纲结果中返回明确标注的全局和文档偏好；实施时选定一种并保证旧全文读取不变。不能先调用全文读取来获取偏好，否则失去节省上下文的目标。当前服务可能仍在内部读取全文并构造评论；阶段一首先承诺减少传给 Agent 的内容，不承诺数据库或内存读取已优化，应测量后决定是否新增底层读取接口。

### 实施与验收

- 先交付契约包、提示生成与一致性检查的现有功能基线，再引入新能力；优先复用现有只读服务接口，在共享 MCP 层实现可纯粹派生的读取功能。Desktop 必要时增加兼容 RPC，DSH 和 Desktop 返回相同语义。
- 修复建议结果中数字建议 ID 被误认为文档 ID，导致文档引用或链接缺失的问题；通过真实服务测试两个宿主的结果。
- 同步任务模板、MCP 说明及 Desktop Skill：按任务选择大纲、分段、文档内定位和指定评论；缺少新工具时回退现有读取。保证自主审阅不处理评论，按评论处理只覆盖用户指定范围，并明确新读取路径如何获取风格偏好。
- 测试空文档、无标题、嵌套标题、围栏代码、重复匹配、中文与 emoji、代理对边界、版本变化、分页及超限。大文档样本比较返回大小、调用次数和阅读正确性，记录测量结果而非预设性能收益。
- 验证已有五个工具、Agent Skill、DSH 工具卡片及用户主动发送评论的行为未回归；新工具不枚举其他文档。真实宿主未验证时明确记录。

## 阶段二：批量建议与审阅反馈

### 用户场景

用户要求修正多处错别字或统一术语时，Agent 能提交一批独立建议；用户逐条审阅后，Agent 能准确解释处理结果并按用户新要求继续。

### 接口草案

| 工具 | 输入 | 返回与约束 |
| --- | --- | --- |
| `space_suggest_batch` | `docId`、`baseVersion`、有序建议数组；每项含独立稳定操作 ID、范围、`expected`、`replacement`、可选说明及评论 ID | 返回每项索引和操作 ID、成功后的建议 ID，或明确失败代码；建议独立呈现给用户。初始方案采用**部分成功**：按输入顺序逐项校验和提交，单项业务错误不阻止后续项；响应丢失时逐项使用相同 ID 和参数重试，不得重复创建。首版不承诺批次级持久身份或原子性。 |
| `space_suggestion_get` 或扩展现有 `space_suggestion_list` | `docId`、建议 ID 或状态过滤、分页 | 返回建议原文、替换内容、说明和当前决策状态；若不存在，返回明确错误。沿用现有状态语义，不把评论处理等同于建议被接受。 |
| `space_review_summary` | `docId` | 返回按状态的建议计数和评论处理状态计数，标明统计时间及正文版本。建议、评论各自变化不一定推进正文版本，计数不应被当作跨调用一致的快照。 |

当前实现的批量接口不接受 `commentId`；评论驱动修改继续通过单条 `space_suggest` 及 `space_comment_complete` 完成。单条建议创建成功但评论关联结果未知时返回已创建的建议和 `commentLink.status: unknown`，用相同操作 ID 和参数重试。现有 MCP 文本结果保留，同时提供对象形式的 `structuredContent`；只读工具提供 annotations，输出 schema 和写入工具 annotations 仍需进一步设计。

批处理的项数和字节上限在实现与测量时确定。单项重放时参数不一致必须报冲突；先前成功项返回原结果，未完成项可继续处理。首版没有持久批次记录，因此不保证批次整体不变、全批次状态查询或不同顺序重放结果相同；客户端必须保存原始请求，重试使用相同顺序、每项 ID 和参数。进程在任意两项之间中断时允许出现部分成功，但不得丢失已确认的建议或重复创建。建议与关联评论仍是独立步骤时，结果必须分别说明两者状态、建议 ID 和可恢复方式，不能把已创建建议隐藏在一个笼统失败中；对中断窗口和重放做故障注入。若无法在现有持久化语义下证明这些保证，则先交付不带评论关联的批处理或推迟该能力，不能宣称原子性。如以后需要批次级身份、参数一致性或状态查询，必须先设计持久化批次记录及恢复语义，并遵守 core 变更同意要求。

用户接受某项建议可能改变正文版本或使其他建议冲突；批次不自动接受、拒绝或重定位，已有版本检查、原文核对和重叠检测继续有效。`space_suggest_validate` 可作为后续增强：预检仅是当时的结果，提交时必须再次校验，不承诺预检后一定成功。

### 实施与验收

- 首先补充现有单条建议与评论关联之间的故障、超时和同 ID 重试测试，梳理现有持久化行为；如需改变 core 行为，先取得明确同意。
- 验证批次内重叠、与已有建议重叠、版本变化、无效范围、重复操作 ID、同 ID 不同参数、单项失败、中断恢复、评论关联失败、并发审阅及跨宿主一致性。
- 验证用户仍能逐条接受或拒绝；状态反馈准确，Agent 不以提交成功声称正文已修改。提供旧客户端继续使用逐条工具的路径。
- 同步全部相关 prompt 和 Skill：指导 Agent 按批次结果逐项确认成功、失败、评论关联与重试；单条工具关联成功后不无条件重复完成，未关联项使用现有完成流程。DSH 卡片只包含本轮实际成功且符合卡片条件的建议；超限和部分成功的展示方式需在实现前定稿。
- 对文本结果保持兼容，评估增加 `structuredContent`、输出 schema 和准确的工具 annotations；annotations 只是客户端提示，不是权限控制。覆盖只读和写入操作的真实行为。

## 阶段三：MCP Apps 审阅预览原型

### 用户场景

Agent 提出修改后，用户可在支持 MCP Apps 的对话里查看文档标题、进度、建议对照与评论关联，并跳转到 CoSpace 进行审阅。首版以只读预览和打开文档为目标。

### 范围与架构

- 在产品边缘或宿主无关的展示适配层提供 MCP Apps 所需的 UI 资源及工具关联；复用共享审阅语义，不让 review core 依赖 MCP Apps 或宿主 SDK。评估复用 `packages/review-ui/` 时继续遵守 [19 · Web Theme Contract](19-web-theme-contract.md) 和现有 token 边界。
- 沙箱页面只展示用户指定文档的必要数据，尽量不声明外部网络域名；按 MCP Apps 规范及实际宿主能力处理 CSP、链接打开和消息通信。不把模型生成的数据当作可信 HTML。
- 首版不提供接受、拒绝、编辑或发送评论操作。未来如需嵌入这些操作，须单独设计可验证的用户直接交互、授权和审计，并复用现有事务；Agent 不能调用决策工具代用户操作。
- 能力协商失败、宿主不支持或资源加载失败时，继续返回现有文本与宿主可用的文档链接。不能假设 WorkBuddy 或 DSH 支持 MCP Apps，须分别在目标版本实测。
- MCP Apps 使用 UI resource 会改变当前“无 MCP resources”的说明：仅在实际启用对应能力时更新 server instructions、Desktop Skill 和宿主文档；UI 资源不等于开放文档资源列表。

### 实施与验收

1. 选定一个已验证支持 MCP Apps 的客户端，制作只读建议对照原型；记录客户端版本、扩展能力和相关 SDK 依赖。比较现有 SDK 与新 SDK 的兼容及打包成本，SDK 迁移作为独立决策，不以发布全部新协议特性为目标。
2. 在 Desktop 与 DSH 分别测试能力发现、预览显示、文档链接、刷新、私有内容隔离和失败回退；尚不支持的客户端验证文本回退。
3. 验证建议中的 Markdown、HTML 和恶意链接不能越过沙箱或未经用户操作触发写入。验证桌面与 DSH 的数据隔离和主题隔离。
4. 根据宿主覆盖率、可维护成本及用户测试决定是否产品化；实验失败不阻塞阶段一、二。

## 交付顺序和验证

阶段一先解决安全定位与读取；阶段二依赖可靠定位，并先明确故障恢复；阶段三依赖可用的建议数据，但原型可并行探索，不阻塞基础能力。每阶段通过短期分支合入 `dev`，随仓库发布流程进入产品；本方案不代表已发布或承诺具体时间。

每阶段至少运行与改动相符的 Node 测试和 `npm run check`；修改 DSH 客户端或打包时运行 `npm run build:client`、`npm run verify:dsh-package`，涉及 Desktop 代理、生命周期或打包时运行对应 Desktop 测试与 smoke。MCP 的双宿主契约、真实宿主版本及未验证项应记录在 PR。真实宿主验证包括工具发现、调用、链接、错误及不支持新能力时的回退；自动化测试不能替代该验证。

每阶段还需验证完整 Agent 流程：自主审阅、指定评论处理、单条与批量建议、部分失败和重试、用户审阅后的反馈；覆盖新旧 Skill 与新旧 MCP 的组合、DSH 卡片和 WorkBuddy 受管理 Skill 升级。自动测试检查生成提示中指定文档与评论 ID、评论正文不外送、能力引用和真实返回契约一致；人工或可复现的目标宿主会话验证模型是否选择正确工具及降级路径，不以字符串匹配代替行为验证。记录各宿主版本、使用的提示入口、结果及无法验证的项目。

2026-11-28 的 DSH 本地构建验收：重载链接到本工作区构建产物的 CoSpace 组件后，在独立 Agent 会话创建测试文档；实测大纲、文档内查找、分段读取、批量建议、建议详情、空评论列表和审阅汇总正常。两条建议保持 pending，正文版本保持 0。此测试未覆盖含评论的宿主交互、旧客户端回退、审阅卡片或文档链接实际打开；WorkBuddy 真实会话不可用，仍需后续验证。自动化测试和打包 smoke 的结果不替代这些宿主验收。

阶段外候选：文档跨版本比较须先确认是否存在可用的历史快照及保留策略；指定多篇文档比较可先复用单篇工具。Resources、prompts 和状态通知须另行评估文档授权、宿主支持、缓存与断线恢复，不能仅因协议支持就默认开放。
