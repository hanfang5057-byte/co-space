# 08 · Markdown 文本审阅内核方案

> 设计提案，尚未实现。当前系统的实际行为仍以 [01](01-domain-model.md)、[02](02-review-loop.md) 和 [07](07-review-core.md) 为准；本方案完成实现和迁移后再更新这些文档。

## 目标与边界

以 Markdown 源文本作为文档的事实源，用统一的文本替换表达建议；界面负责渲染和展示差异。新增、删除、修改列表及其项目、标题、引用、代码块或表格，都使用同一种审阅模型，不依赖对每种语法实现结构性修订。Markdown 方言、渲染器与所支持的扩展另行明确；源文本能保存某种写法不代表渲染器必然支持它。

Agent 可以创建含完整初始内容的新文档；已有正文只能提交建议，由用户逐条接受或拒绝。评论是用户内容，只在用户主动操作时发送。保留持久化、并发控制、操作幂等、重启恢复和冲突时不猜测的约束。

## 数据模型

- **文档**：稳定 ID、已接受 Markdown 文本、正文版本 `contentVersion`、审阅状态版本 `reviewVersion`。新建时两者初始化；接受改变正文时递增正文版本，提交和决策建议时递增审阅状态版本。版本细节须在接口中统一定义，避免以一个版本冒充另一个。
- **建议**：稳定 ID、文档 ID、状态、创建顺序、基准正文版本、基准范围 `[from, to)`、预期原文、替换文本、前后上下文，以及当前可用的映射锚点。状态至少有 `pending`、`accepted`、`rejected` 和 `conflicted`；冲突建议保留内容但不可直接接受。一个建议是一个独立用户决策单位，不因相邻而自动合并。
- **操作记录**：稳定 `operationId`、请求指纹和提交结果。相同请求重试返回原结果，同 ID 不同请求返回冲突。
- **正文变更历史**：保留足以将基准版本锚点映射到当前版本的变更及顺序信息；若历史不可用或无法可靠映射，标记冲突，不能猜测。压缩策略必须保证仍被待处理建议或评论引用的历史可用，或先安全转换这些锚点。

所有范围以对应版本的**已接受 Markdown 源文本**为基准，采用 UTF-16 代码单元、左闭右开区间，与 JavaScript 字符串索引一致。校验范围时不得拆分代理对；接口应提供文本片段及坐标或辅助定位，避免 Agent 手算。换行在创建时确定并持久化（建议统一为 LF）；不能在后续无版本变更时暗中归一化。不存在跨版本可直接复用的裸坐标。

新增、删除和修改统一为替换：插入为 `from === to` 且原文为空；删除的替换文本为空；修改的原文和替换文本均非空。提交时必须验证范围中的内容等于预期原文，空替换且空原文属于无效操作。

## 提交与并存规则

Agent 先读取正文、版本及待处理建议，再提交基准版本、范围、预期原文和替换文本。服务端在同一写事务内定位、验证、检查冲突并持久化；提交成功不改变已接受正文。

| 相互关系 | 规则 |
| --- | --- |
| 非空范围互不相交 | 允许，包含首尾相接 |
| 非空范围相交，包含一方包含另一方 | 冲突，拒绝后提交的建议并返回已有建议 ID |
| 插入点在非空范围内部 | 冲突 |
| 插入点在非空范围起点或终点 | 允许；起点归范围之前，终点归范围之后 |
| 多条建议在同一插入点 | 允许；以事务内分配的稳定创建序号确定顺序 |

同点插入的顺序是文档顺序，必须在预览和最终正文一致，并且不受用户接受顺序影响。例如先后建议在同一点插入 `B`、`C`，即使先接受 `C` 再接受 `B`，结果仍为 `BC`。因此不能仅保存当前数字偏移：需记录插入点的稳定身份、排序序号和已接受同点插入的来源及长度，决策时根据这些信息计算落点。插入锚点与正文变更历史一同持久化，跨重启保持结果。并发提交的顺序以数据库事务中分配的序号为准。

边界归属也须贯穿位置映射：在范围起点插入的内容位于该范围之外且在其前；在终点插入的内容位于其外且在其后。相邻范围的共同边界上插入，位于左侧范围之后、右侧范围之前。每种接受顺序均应保留这些关系。

当前第一版对真正重叠的建议返回冲突，不保存互斥候选；用户可让 Agent 基于现状重新提出。后续若需要保存互斥候选，须另行设计状态和选择界面。

## 版本变化与重定位

读取和提交分别携带正文版本及审阅状态版本。审阅版本变化时重新检查全部活动建议的冲突；正文版本变化时先尝试通过完整变更历史映射基准锚点，再核对预期原文和冲突。若无可靠映射，可结合持久化的前后上下文尝试唯一定位；仅有唯一、可验证的匹配且不存在冲突时才可继续。纯插入原文为空，必须验证锚点及前后上下文，不能凭空串唯一匹配。

自动重定位只能调整锚点，不能更改原文、替换内容或建议身份。重复文本、上下文不足、范围被其他变更触及、历史缺失或多个候选均须拒绝提交或把已有建议标记为 `conflicted`；保留内容供用户查看并重新提出。不能声称上下文唯一就能证明语义一定正确，具体验证阈值应通过测试与产品设计确定。

## 用户决策与事务

接受建议时，在事务内重新读取当前状态，验证建议仍为待处理、锚点有效、预期原文相等及相关冲突规则；然后应用替换，更新正文版本、建议状态、变更历史、其他建议和评论锚点及审阅版本，最后记录幂等结果。结果只能在提交事务后返回。不能确认安全时回滚或将建议标记冲突，不能修改正文。

拒绝仅关闭选中的建议并递增审阅版本，不改变正文或正文版本。重复决策不得重复应用；并发决策由事务串行化。对于已持久化但无法安全映射的其他建议，保留其 ID、原文和替换内容并标记冲突。确保任意顺序接受独立建议时最终正文与展示的顺序一致；接受一条不能丢弃其他建议或改变未接受内容。

## 接口、界面与评论

- **MCP**：读取接口返回 Markdown、双版本、建议及可使用的定位信息；提交接口接收文本替换，而非富文本文档 step。定义冲突、版本过期、定位失效等明确错误码和冲突 ID；不提供 Agent 直接修改或决策已有正文的接口。
- **界面**：默认渲染已接受正文；建议以原文／替换文本 diff 和位置展示，必要时提供渲染预览。新增内容须明确标识为建议；用户逐条接受或拒绝。Markdown 源码到渲染内容的选区映射须单独设计，不能假设 DOM 字符偏移等于源码偏移。
- **评论**：保存用户选区对应的 Markdown 源码锚点、引用和上下文；正文变更后映射未受影响的锚点。引用被删除、来源映射不明或结果不唯一时保留评论并标记失效。评论只因用户主动发送动作送入会话；保留既有发送结果未知和幂等处理。
- **安全与渲染**：制定 Markdown 方言、HTML、链接和图片的渲染策略；不把不可信内容作为未经处理的 HTML 插入界面。源文本保存能力与预览能力分开声明。

## 迁移与交付

1. 独立实现并验证新文档的 Markdown 文本审阅闭环，先覆盖多个建议的提交、决策、映射、评论和恢复。
2. 设计旧富文本数据库的内容转换，并逐篇验证内容、结构和格式损失。已接受正文的转换也未必能原样往返。
3. 对旧的待处理建议和评论单独验证语义及坐标映射；不能证明安全时保留原库和原记录，报告无法迁移的文档，不静默丢弃、接受或拒绝。迁移须可重复、可恢复，切换前备份并验证。
4. 完成接口、客户端和宿主集成后，更新现有规范；真实宿主端到端结果单独记录。

## 验收

- 对整个列表、单个列表项及普通文本的增删改，均可提交并由用户独立接受或拒绝；同样覆盖标题、代码块和表格源码。
- 10–20 条独立建议并存；不同接受／拒绝顺序产生一致且可预测的正文；相邻范围、边界插入、同点插入及其所有决策顺序正确。
- 重叠、插入范围内部、重复文本、过期版本、历史缺失和上下文歧义均安全处理；建议 ID 和内容不被静默改变。
- 覆盖中文、表情符号、换行、空文档、文首文末；不拆分 UTF-16 代理对。
- 评论在相邻编辑、引用删除和无法定位时状态正确；发送仍由用户主动触发。
- 幂等重试、并发提交与决策、进程中断和重启恢复保持事务完整性；旧数据迁移可回退且不丢失待处理内容。
