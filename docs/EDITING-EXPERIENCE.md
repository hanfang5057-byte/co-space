# 完整的文档编辑体验 · 第一性原理方案

> 状态：方案（未实施）
> 对象：`@local/dsh-space`（DSH 的 Markdown 文档空间插件）
> 目标：把"能编辑"提升为"敢托管"——人、Agent、其他设备同时参与时，内容不丢、改了能看见、错了能退回、冲突不静默。

---

## 1. 目标与非目标

### 目标

一个**完整的文档编辑体验**，指下面这条闭环每一步都成立：

> 打开 → 读懂 → 修改 → 被保存 → 被他人/Agent 看见 → 被审阅 → 可回退 → 不互相覆盖

### 非目标（本方案明确不做）

| 不做 | 理由 |
|---|---|
| 字符级实时协同（CRDT/OT） | 与"文件是真相源、任何编辑器可打开、Syncthing 同步"这三个前提冲突，代价是整篇文档换存储模型 |
| 富文本属性（字体/字号/颜色/高亮/下划线/段落对齐） | 无 Markdown 语法；写 HTML 会破坏开放文本契约 |
| 评论/批注线程 | 需要独立的旁路存储与通知模型，可单独立项 |
| 服务端渲染/发布站 | 与编辑体验无关 |

## 2. 第一性原理：四条事实，七条不变式

不从功能清单出发，而从四个不可再简化的事实出发。

### 事实

1. **真相是字节。** 文档的权威表示是磁盘上的 `.md`；编辑器、索引、presence、版本库都只是它的派生物。
2. **编辑是一个函数。** `f(state, intent) → state'`，一次编辑只有三种可观察结果：内容变了、产生了一个版本、有人收到了通知。
3. **写者不可靠。** 人会走神、Agent 会幻觉、网络会断、进程会被杀。
4. **信任来自可预期。** 用户对编辑器的信任不是"功能多"，而是"不丢、能退、看得见"。

### 不变式（由事实推出，方案必须逐条满足）

| 编号 | 不变式 | 违反它的后果 |
|---|---|---|
| I1 | **保真**：进入编辑器再出来的 Markdown，除用户显式修改外语义不变 | 用户不敢用（"我的文件被改了"） |
| I2 | **归因**：每个内容状态都能回答"谁、何时、基于哪个版本" | 出了问题无法追责与回滚 |
| I3 | **排他或收敛**：同一时刻只有一个写者，或所有写者的结果确定收敛 | 静默覆盖，最严重的信任崩塌 |
| I4 | **可逆**：任一改动都能被撤销，且撤销本身可被追溯 | Agent 一次误改就不可收拾 |
| I5 | **可观**：他人的改动在有界时间内可见 | 两个人以为在协作，其实各写各的 |
| I6 | **可寻址**：Agent 能按结构定位文档（块/章节），而不是整篇覆盖 | Agent 只能"重写全文"，风险极高 |
| I7 | **可审**：提议在落地前可被审视，结论可被记录 | 人无法判断 Agent 改了什么 |
| I8 | **不销毁**：删除、清理、覆盖都可恢复 | 一次误操作造成不可逆损失 |

### 由此得到的唯一自洽架构

- 并发 → **排队**：用租约（lease）把"同时写"变成"先后写"，而不是用 CRDT 去合并。
- 丢失 → **留痕**：用内容寻址版本库把"覆盖"变成"新增版本"。
- 信任 → **可见**：用 diff、归属、presence 把"黑箱"变成"可审"。
- 覆盖 → **分块**：用结构化寻址把"整篇重写"变成"定点修改"。

这四条正是当前插件的骨架（`.live/{locks,versions,proposals}` + `doc_patch` + SSE），本方案是把骨架补成完整体，而不是换骨架。

## 3. 现状盘点：哪些不变式还没满足

以本仓库代码为证据（行号为撰写时快照）。

| 不变式 | 现状 | 证据 |
|---|---|---|
| I1 保真 | ⚠️ 部分 | 列表标记 `-` 被规范化成 `*`（实测）；Crepe 把图片缩放比例写进 `alt`（`![1.00](…)`）；是否出现 `<br />` 取决于编辑路径，缺语料验证 |
| I2 归因 | ⚠️ 部分 | `recordVersion()` 记录 `writer/by`，但**人类保存不写版本**：UI 保存走 `write` → `writeFile`，只有 `doc_patch`/`doc_restore` 调 `recordVersion`（`server/api.mjs:129`、`server/core/files.mjs:93`） |
| I3 排他 | ❌ 有缺口 | 租约只被 `doc_patch` 检查；`writeFile` 不校验租约，只靠 `expectedSha256` 的乐观并发（`files.mjs:93`） |
| I4 可逆 | ⚠️ 部分 | "撤销上一步"= 恢复上一个**已记录**版本；人类编辑不进版本库时，撤销会跳过人类改动 |
| I5 可观 | ✅ 基本满足 | SSE `doc-change/presence/proposal` + 5 s 轮询兜底；presence 粒度是**章节**（最近标题），不是块 |
| I6 可寻址 | ❌ 有隐患 | `blockId = section:index`，由解析时的序号派生（`docs.mjs:56`）；文档一改，Agent 缓存的 id 可能指向另一个块 |
| I7 可审 | ❌ 缺失 | 提议是 `ops` 列表 + 一句理由；人只能读描述，看不到真实 diff |
| I8 不销毁 | ❌ 有缺口 | `deleteFile` 直接 `fs.rm`，不进回收站（`files.mjs:151`）；只有旧格式清理走 trash |

**结论**：骨架正确，但 I3/I6/I7/I8 是硬缺口，I1/I2/I4 是软缺口。下列分阶段方案按"先堵硬缺口、再补软缺口、最后提升体验"排序。

## 4. 五个不可动摇的设计决策

1. **文件是唯一真相。** 版本、租约、presence 都放在 `.live/` 旁路目录，可由文件系统重建；任何时候删掉 `.live/`，文档仍然可读可编辑（只是失去协作能力）。
2. **单写者排队，不做自动合并优先。** 默认路径是"请求编辑权 → 获得 → 写 → 释放"；三方合并只在**接管**和**分区恢复**两个场景作为兜底，并必须让人确认。
3. **Markdown 定义"规范形"，而不是追求字节不变。** 明确列出允许的规范化（列表符号、围栏语言、行尾、空行折叠），其余一律视为 bug；用固定语料做往返测试。
4. **Agent 与人是对等写者。** 同一个租约、同一套版本、同一套提议；Agent 不享有特权通道，唯一区别是同设备时可继承人的租约。
5. **提议即补丁，不是描述。** 提议必须能渲染成 diff、能按 hunk 接受，而不是一段自然语言。

## 5. 目标模型

### 角色

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 读者 | 读、跟读、看历史、看 diff | 写 |
| 编辑者（人） | 持租约写、发起提议、接受提议、恢复版本 | 越过他人租约写 |
| Agent | 读块、持租约 `doc_patch`、发起提议 | 越权写、静默删除 |
| 接管者 | 在租约过期/强制时接管，先留存快照 | 静默覆盖（必须留版本） |

### 文档状态机

```
        ┌─────────────── free ───────────────┐
        │                                    │
   acquire│                            release│
        ▼                                    │
     leased(holder, expiresAt) ──expire──► stale
        │                                    │
        │ takeover（先快照）                  │
        └──────────────► leased(newHolder) ◄─┘
```

### 数据布局（保持现状，补字段）

```
<space>/
  pages/*.md                 正文（唯一真相）
  assets/*                    图片（上传落盘）
  .live/
    versions/<docId>/<sha>.md 内容寻址版本
    heads/<docId>/<writer>.json 每写者指针（含 by/at/sha）
    base/<docId>.json         合并基点
    locks/<docId>/<lease>.json 编辑权
    presence/<device>.json    心跳（doc、section、mode）
    proposals/<docId>/*.json  提议（ops + rationale + baseSha）
    log/<docId>.jsonl          【新增】变更日志：who/what/when/sha
    trash/<docId>/<ts>/        【新增】删除与覆盖的回收站
```

## 6. 分阶段方案

每阶段都给出**可执行验收**（能变成脚本断言），而不是"做完了"。

### P0 · 堵住硬缺口（I3 / I8 / I2）

**问题**：越权写、删除不可恢复、人类改动不入版本。

**做法**

1. `writeFile` / `editFile` / `deleteFile` / `moveFile` 全部增加租约校验：
   - 有租约且 holder ≠ 调用者（且 device 不同）→ `LOCKED`，附带 holder/label/expiresAt；
   - MCP 工具自动继承同设备租约（已有 `device` 字段）。
2. 删除改为两段式：`fs.rename` 到 `.live/trash/<docId>/<ts>/`，30 天内可 `restore`；`.live` 不参与 `trash` 清理。
3. 人类保存也写版本：`write` 成功后 `recordVersion(..., { writer: deviceId, by: 'human' })`。

**验收**

- 他机持锁时，`write/edit/delete` 均返回 `LOCKED`（脚本断言）；
- 删除任意文件后，`trash` 中出现副本且 `restore` 可恢复原文（sha 相同）；
- 人类保存后 `doc_versions` 出现该 sha，且 `by === 'human'`。

### P1 · 可审（I7）

**问题**：提议只有操作描述，人无法判断。

**做法**

1. 提议落地前生成 diff：`base`（发起时的 sha）→ `proposed`（应用 ops 后的全文）→ 使用 `@milkdown/kit/plugin/diff` 的 `computeDocDiff` 渲染块级差异。
2. 审阅 UI：左"当前"右"提议"，逐 hunk 接受/拒绝；接受时重新校验 `baseSha`（防止审阅期间文档已变）。
3. 版本历史同样支持 diff（任选两个 sha 对比）。

**验收**

- `doc_proposals` 返回的每条提议附带 `diff: [{ kind: 'add'|'del'|'change', before, after }]`；
- UI 中拒绝某 hunk 后，最终内容只保留被接受的 hunk（脚本断言文件内容）；
- 审阅期间文档被他改：接受返回 `VERSION_CONFLICT` 并提示重新审阅。

### P2 · 可寻址与归因（I6 / I2 / I5）

**问题**：块 id 会漂移；presence 只到章节；没有"谁改了什么"的流水。

**做法**

1. **块锚点协议**：`blockId` 保留给人读，但写操作必须带 `anchor`（该块首行的文本 hash 或前 12 字），服务端命中则执行，未命中返回 `ANCHOR_MOVED` + 当前块列表。拒绝"按序号猜"。
2. **变更日志**：每次成功写入追加 `.live/log/<docId>.jsonl`：`{at, actor, kind, sha, ops?, anchor?, summary}`；`doc_history` 工具按时间倒序返回，UI 侧栏显示"最近变更"。
3. **块级 presence**：客户端从 ProseMirror 选区映射到"块文本 hash"，presence 上报 `blockAnchor` 而非标题；远端据此在块左侧显示"某人正在看"。

**验收**

- 用 P0 的文档做插入/删除后，旧 `blockId` 失效但 `anchor` 仍命中同一块（脚本断言）；
- 连续三次编辑后 `doc_history` 返回三条且 actor 正确；
- 两个浏览器分别把光标放在不同块，presence 返回两个不同 `blockAnchor`。

### P3 · 编辑体验（I1 / I4 / 体验）

**问题**：往返有损、撤销粒度粗、缺常用编辑能力。

**做法**

1. **保真语料 + 往返测试**：`test/fixtures/markdown/*.md` 覆盖标题层级、嵌套列表、任务清单、表格对齐、围栏语言、引用嵌套、HTML 内联、中文标点、行尾空格、`<br />`。断言 `normalize(roundtrip(x)) === normalize(x)`，其中 `normalize` 是**显式**的规范形（列在文档里）。
2. **细粒度撤销**：`撤销上一步` 改为按 `log` 的最后一条操作逆运算（块级），而不是恢复整篇版本；提供"撤销该 Agent 的这批改动"。
3. **常用能力**：查找替换、大纲导航（标题树跳转）、代码块语言选择器、表格列宽拖拽（Crepe 组件已具备，只差配置）。
4. **图片**：`alt` 不再存缩放比例（改为 `title` 或 sidecar），保持 `![说明](assets/x.png)` 干净。

**验收**

- 语料全部通过往返断言（CI 阻断）；
- 撤销一条块级改动后，文件只回退该块（diff 断言）；
- 查找替换在 10 万字文档中 p95 < 200 ms。

### P4 · 分区与冲突（I3 的兜底）

**问题**：网络分区时两边都以为自己持锁。

**做法**

1. 租约判定用 `acquiredAt + leaseId` 全序（已有），但**接管必须留快照**并写 `log`；
2. 分区恢复后若检测到 `heads` 分叉：不做静默合并，而是生成"冲突提议"——两侧内容 + 三方合并结果，由人选择；
3. 提供 `doc_conflicts` 工具与 UI 入口（复用现有冲突对话框语义）。

**验收**

- 模拟两设备并发写：恢复后必产生一条冲突记录，且没有任何一方内容丢失（两侧 sha 都在 `versions`）；
- 选择任一侧后，文件内容与所选 sha 一致。

## 7. 度量（把"体验"变成可测的数）

| 指标 | 定义 | 目标 |
|---|---|---|
| 保真率 | 语料往返断言通过比例 | 100% |
| 越权写 | 非持锁者成功写入的次数 | 0 |
| 静默覆盖 | 无冲突记录的内容替换次数 | 0 |
| 可见延迟 | 他人改动到本端出现 | p95 < 2 s |
| 保存延迟 | 停止输入到落盘 | p95 < 800 ms |
| 审阅成本 | 提议从生成到决策的点击次数 | ≤ 3 |
| 可恢复性 | 删除/覆盖后可恢复比例 | 100%（30 天内） |

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 租约过严导致"想改不能改" | 体验断点 | 到期自动释放 + 一键接管（先快照）+ 明确倒计时 |
| 轮询兜底带来 IO 压力 | 大空间卡顿 | 快照只取 `mtime:size`、限深 6、可配置间隔；目录级增量 |
| diff 审阅被大改淹没 | 审阅疲劳 | 按块折叠、只展开变更 hunk、支持"全部接受" |
| 规范形定义过宽 | 丢失用户格式 | 语料先行；规范形写进文档并由 CI 守护 |
| Agent 误用块锚点 | 改错块 | 锚点未命中直接失败并返回候选块，不做模糊匹配 |

## 9. 里程碑与"完成"定义

| 里程碑 | 内容 | 出口条件 |
|---|---|---|
| P0 | 租约全覆盖、删除进回收、人类保存入版本 | 三条验收脚本通过 |
| P1 | 提议 diff + hunk 接受 + 版本对比 | 三条验收脚本通过 |
| P2 | 锚点协议、变更日志、块级 presence | 三条验收脚本通过 |
| P3 | 保真语料、细粒度撤销、查找替换/大纲 | CI 保真率 100%，其余验收通过 |
| P4 | 冲突工作流 | 双设备并发脚本通过 |

**"完整文档编辑体验"完成定义**：下列用户旅程全部可走通且可回归测试——

1. 新写一篇 → 自动保存 → 关掉重开内容一致；
2. 另一人只读跟读，能看到"谁在看哪一段"；
3. 另一人请求编辑权 → 我这边自动只读并提示；
4. Agent 按块改三处 → 我能看到 diff 并逐条接受/拒绝；
5. 我误删一段 → 一键撤销只回退这一段；
6. 我把文件删了 → 回收站能找回；
7. 断网在两边各改一段 → 恢复后必须让我选，不静默合并；
8. 我用别的编辑器改文件 → 空间里 5 秒内可见。

## 10. 与现有实现的关系

本方案不推翻现有设计，只补四个硬缺口（I3/I6/I7/I8）和三个软缺口（I1/I2/I4）：

- 保留：`.live/` 文件布局、租约语义、SSE + 轮询、`doc_patch` 的 CAS、Crepe 编辑面。
- 新增：租约校验中间件、`.live/trash`、`.live/log`、`anchor` 协议、diff 渲染、保真语料。
- 修改：`writeFile`/`deleteFile` 的写路径；人类保存的版本记录；presence 的粒度。

预计工作量：P0 约 1 天，P1 约 2 天，P2 约 2 天，P3 约 2 天，P4 约 1 天（单人节奏，含验证脚本）。
