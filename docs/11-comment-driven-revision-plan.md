# 11 · 基于评论工具的文档修改方案

> 状态：设计提案，尚未实现。范围包括 DSH 与 WorkBuddy Connector；不改变“Agent 提建议、用户决定是否接受”的文档权限边界。

## 目标

把当前“把评论全文拼进会话提示词”的流程，改为“用户显式发起处理请求，Agent 调用 Space 评论工具读取待处理评论，再按评论提交建议”。评论保留在文档侧，作为有 ID、有锚点、有状态的工作项；会话只携带文档引用和简短的处理指令。

用户仍须明确触发处理。Agent 读取评论不代表用户授权直接改写文档；对已有文档的修改仍只能通过 `space_suggest` 提交为建议，最终由用户在审阅界面接受或拒绝。评论内容是不可信的用户输入，工具说明必须要求将其视为修改需求而非对权限规则的覆盖。

## 当前行为与缺口

- DSH 的“全部发送”调用 `sendComments`，将评论正文、引用和处理要求组合为一条会话消息；`space_document_read` 随后读取文档，Agent 再提交建议。
- WorkBuddy 当前将评论保存在本机审阅页；没有向对话发送评论或从 Agent 工具读取评论的能力。
- 共享 MCP Server 已向两个宿主提供文档读取、建议提交和建议状态查询，但没有评论读取/处理工具。
- 评论状态目前服务于 UI 展示和 DSH 的消息发送记录，不能准确表达 Agent 已领取、建议已生成或处理需要重试。

## 目标用户流程

### DSH

1. 用户在文档审阅界面选择 **让 Agent 处理评论**，确认本次待处理评论范围。
2. DSH 仍通过宿主会话 API 发起当前会话请求，但只发送 `space:<docId>` 与一句处理指令，不内嵌评论正文。
3. Agent 调用 `space_document_read` 读取最新正文与版本，并显式请求附带待处理评论。
4. Agent 针对每条可执行评论逐条提交建议；多条评论可以合并为同一修改，但需保留每条评论与建议的关联。不能安全定位或意图不清的评论需在回复中说明，留待用户补充。
5. Agent 通过处理结果工具记录建议关联和完成状态，回复建议摘要及审阅入口。正文仍未改变，直到用户逐条决策。

### WorkBuddy

1. 用户在本机审阅页点击 **让 Agent 处理评论**；页面显示待处理数量和本次将提交给 Agent 的内容范围。
2. 因普通 Connector 没有受支持的会话注入能力，界面展示一段短提示词和 **复制** 操作。用户手动粘贴到 WorkBuddy 当前对话并发送。
3. 提示词只包含 `space:<docId>` 与调用 `space_document_read` 读取评论的要求；Agent 经 Connector MCP 工具读取评论并提交建议。
4. Agent 使用与 DSH 相同的工具记录处理结果；用户回审阅页查看并决策。

WorkBuddy 路径继续采用用户手动发送作为传输手段；评论正文由 MCP 工具按需读取，不放入剪贴板中的提示词。后续若 WorkBuddy 为 Buddy App 提供合适的产品分发入口，可单独评估 JSSDK 预填，但不作为本方案依赖。

## 工具与契约提案

不新增 MCP 工具。扩展现有 `space_document_read` 与 `space_suggest`，在 `packages/transport-mcp/server.js` 中统一实现，DSH 与 WorkBuddy 复用同一契约；两者仍绑定各自 SpaceService 和独立数据库。

本次改造同时要求精简现有工具清单。移除 `space_list` 和 `space_documents`：Agent 不枚举文档，只能读取和建议修改用户明确指定的 `space:<docId>` 文档。没有指定文档时，Agent 应询问用户或请用户从 Space UI 选择，不得自行搜索、挑选文档。显式创建新文档仍由 `space_document_create` 支持。WorkBuddy 专属的 `space_status` 与 `space_review_open` 都启动/检查审阅 sidecar 并返回状态或页面地址；合并为一个 `space_review_open`，保留可选文档 ID，并在返回中包含可用状态。完成后 DSH 从 6 个降为 4 个 MCP 工具，WorkBuddy 从 8 个降为 5 个。

目标清单如下：

| 目标工具 | 宿主 | 说明 |
|---|---|---|
| `space_document_create` | DSH、WorkBuddy | 创建文档 |
| `space_document_read` | DSH、WorkBuddy | 读正文/建议；按需用 `includeComments` 读取评论 |
| `space_suggest` | DSH、WorkBuddy | 提交建议；可选关联评论 ID |
| `space_suggestion_list` | DSH、WorkBuddy | 查询建议状态及评论关联 |
| `space_review_open` | WorkBuddy | 打开审阅页并返回服务可用状态 |

工具数量减少不得合并不同的领域动作（例如建议提交与建议查询），也不得删除用户决策边界、显式创建或指定文档读取能力。MCP 不提供文档枚举入口。

| 现有工具 | 提案调整 | 关键契约 |
|---|---|---|
| `space_document_read` | 增加可选 `includeComments` 参数 | 默认 `false`，保持普通文档读取的输出和上下文开销；用户明确要求处理评论时传 `true`，返回该文档尚未关联建议的评论、稳定评论 ID、引用、锚点有效性和状态 |
| `space_suggest` | 增加可选 `commentIds` | 建议可以声明对应的一条或多条评论；服务端验证评论属于同一文档，并在同一事务内提交建议和关联，重试保持幂等 |
| `space_suggestion_list` | 保持现状，可用已有建议历史核对处理结果 | 每条建议包含关联评论 ID；Agent 和 UI 可从建议历史追踪哪些评论已经产出建议 |

`includeComments` 使用显式 opt-in，避免普通的文档阅读自动把批注带进上下文或被误认为处理请求。Agent 只有在用户发起评论处理时，才读取评论并把来源评论 ID 带入建议。无法安全转成建议的评论不关联建议，保持待处理；Agent 回复说明需要澄清的原因。用户补充或编辑评论后可再次发起处理。

评论是否已有建议关联由持久化的评论—建议关系判断，不另造 claim/complete/list 工具或一套独立批次状态。关联只表示 Agent 已提交建议，不代表正文已修改，也不代表建议已接受；UI 继续展示评论及其建议的决策状态。多个建议可关联同一评论；一个建议可关联多条评论，以支持拆分和合并处理。

## 一致性、安全与失败处理

- 每条评论有稳定 ID；建议提交沿用 Space 的幂等操作 ID。`commentIds` 的校验、建议持久化与评论关联必须原子提交；相同操作重试不得重复创建建议或关联。
- 同一评论可能由多个建议分别落实；已关联评论仍应可从显式读取结果和建议历史追踪。Agent 再次处理时默认只读取尚无建议关联的评论；用户明确要求重做时，应先检查已有建议与决策，避免机械重复。
- 读取评论时同时返回文档当前版本。锚点失效时将评论的引用和失效标志交给 Agent，要求重新定位；禁止将猜测的范围提交为建议。
- Agent 只能读评论、提建议并关联建议；工具不提供接受/拒绝建议或直接改正文的能力。
- 评论文本可能包含越权指令。系统工具说明和 Skill 必须将评论视为用户提供的文档修改意见，并继续执行既有工具权限边界。
- 不将评论内容写入日志或非本机云端存储。WorkBuddy 仍仅在其隔离的本机 Space 中访问评论。
- MCP 工具失败、会话中断或结果未知时，评论仍保留为待处理；重试复用建议操作 ID或先检查建议历史，不得静默认为建议已提交。

## 分宿主适配

| 层 | DSH | WorkBuddy |
|---|---|---|
| 触发 | 审阅 UI 的显式操作；宿主 API 只发送引用和工具调用指令 | 审阅 UI 生成引用和短提示词，用户复制并手动发送 |
| 评论读取 | 用户显式触发后，Agent 调 `space_document_read(includeComments: true)`；DSH UI 继续显示本地评论状态 | 用户手动发送复制提示词后，Agent 调同一工具参数；本机 Web UI 显示同一状态模型 |
| 处理状态 | `space_suggest` 原子记录评论—建议关联；DSH UI 刷新显示关联建议及决策状态 | WorkBuddy 独立 review-core 数据库记录评论—建议关联；本机 UI 刷新显示关联建议及决策状态 |
| 对话能力 | 保留 DSH 当前会话选择和发送能力，但不再传评论正文 | 不增加非公开 API、对话数据库或 UI 自动化依赖 |

## 实施阶段

1. **契约与关联模型**：确定评论读取筛选、评论修改后重开规则、部分成功处理，以及建议与评论的关联形态。
2. **共享核心与 MCP**：在 `space_document_read` 增加 opt-in 评论读取，在 `space_suggest` 增加可选评论关联，并在 review-core 中原子持久化关联；不新增 MCP 工具。移除 `space_list` 与 `space_documents`，更新 MCP instructions 和中英文 Skill，要求 Agent 只处理用户指定的文档。该阶段会改变评论读取或建议持久化行为；按仓库 `AGENTS.md`，实施前必须另行取得用户明确同意。本提案本身不授权这些改动。
3. **WorkBuddy 工具收敛**：移除 `space_status`，将可用状态合并进 `space_review_open` 响应。
4. **DSH UI 接入**：替换当前全文发送为显式处理请求；显示执行进度、关联建议、失败与重试状态；继续使用 DSH 当前对话。
5. **WorkBuddy UI 与文案**：添加评论处理提示词复制、评论处理状态和建议关联；保留手动粘贴发送路径。
6. **验证与宿主验收**：覆盖幂等、并发、进程中断、锚点失效、部分完成和重试；在 DSH/WorkBuddy 实际宿主中分别验证目标工具清单、评论读取、建议生成及 UI 状态刷新。

## 验收标准

- 会话消息/复制提示词中不包含评论正文；Agent 必须通过评论工具读取本次评论。
- 用户没有显式发起时，Agent 不会通过 `space_document_read` 请求评论内容或处理评论。
- 两个宿主使用同一套评论处理契约，但数据目录、文档和评论保持隔离；Agent 不能枚举文档，只处理用户明确指定的文档。
- 每条已完成评论可追溯到一个或多个建议 ID；用户能在 UI 区分建议生成、用户决策和正文已接受三种状态。
- 相同操作重试不重复生成建议；处理中断和结果未知可恢复；失效锚点不会导致猜测式修改。
- Agent 从不直接修改已有文档正文，仍由用户接受或拒绝每条建议。

## 待定决策

- 是否允许一次只处理用户勾选的部分评论，还是仅支持全部 pending 评论。
- 同一评论可生成多个建议时，评论与建议关联采用一对多；多条评论合并成一个建议时是否允许多对多关联。
- `needs_clarification` 由用户补充原评论、追加回复，还是关闭旧评论并新建评论。
- 用户在 Agent 处理期间删除或编辑评论时的冲突策略。
- DSH 的现有 **全部发送** 文案是否改为 **让 Agent 处理评论**，以及是否需要独立的“复制处理提示词”入口。
