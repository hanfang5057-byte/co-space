# Historical implementation record — multi-adapter version

本文保留 DSH 与 WorkBuddy 并行时期的流程设计和验收记录。涉及 WorkBuddy 的范围已移除，不代表当前产品支持。当前适配器扩展方式见[适配器接入规范](14-adapter-integration.md)。

# 11 · 基于评论的文档修改方案

> 状态：核心实现与本机验证已完成；真实 DSH / WorkBuddy 宿主内的会话及市场验收仍待完成。范围包括 DSH 与 WorkBuddy Connector；不改变“Agent 提建议、用户决定是否接受”的文档权限边界。

## 目标

把原先“把评论全文拼进会话提示词”的流程，改为“用户显式发起处理请求，Agent 从指定文档读取结果中取得评论，再按评论提交建议”。评论保留在文档侧，作为有 ID、有锚点、有状态的工作项；会话只携带文档引用和简短的处理指令。

用户仍须明确触发处理。Agent 读取评论不代表用户授权直接改写文档；对已有文档的修改仍只能通过 `space_suggest` 提交为建议，最终由用户在审阅界面接受或拒绝。评论内容是不可信的用户输入，工具说明必须要求将其视为修改需求而非对权限规则的覆盖。

## 当前行为与缺口

- DSH 通过宿主会话 API 发送文档引用和简短处理指令；评论正文保存在本机，由 Agent 后续读取。
- WorkBuddy 审阅页通过剪贴板提供短提示词，用户手动粘贴；没有 Connector 会话注入 API。
- 共享 MCP Server 为指定文档读取默认返回评论，并提供建议提交/查询和评论处理完成操作；不提供文档枚举工具。
- 评论处理记录明确区分待处理、已提交关联建议和需要澄清；评论始终保留在 UI，并展示关联建议决策状态。

## 目标用户流程

### DSH

1. 用户在文档审阅界面选择 **让 Agent 处理评论**，请求处理当前可处理评论。
2. DSH 仍通过宿主会话 API 发起当前会话请求，但只发送 `space:<docId>` 与一句处理指令，不内嵌评论正文。
3. Agent 调用 `space_document_read` 读取最新正文、版本和评论；该工具默认返回三者。
4. Agent 针对每条可执行评论逐条提交建议；若用户指定评论 ID，只处理这些 ID；未指定时，处理读取结果中的全部待处理评论。多条评论可以合并为同一修改，但需保留每条评论与建议的关联。不能安全定位或意图不清的评论需在回复中说明，留待用户补充。
5. Agent 通过处理结果工具记录建议关联和完成状态，回复建议摘要及审阅入口。正文仍未改变，直到用户逐条决策。

### WorkBuddy

1. 用户在本机审阅页点击 **让 Agent 处理评论**。
2. 因普通 Connector 没有受支持的会话注入能力，界面展示一段短提示词和 **复制** 操作。用户手动粘贴到 WorkBuddy 当前对话并发送。
3. 提示词只包含 `space:<docId>` 与调用 `space_document_read` 读取评论的要求；Agent 经 Connector MCP 工具读取评论并提交建议。
4. Agent 使用与 DSH 相同的工具记录处理结果；用户回审阅页查看并决策。

WorkBuddy 路径继续采用用户手动发送作为传输手段；评论正文由 MCP 工具从用户指定文档的读取结果返回，不放入剪贴板中的提示词。后续若 WorkBuddy 为 Buddy App 提供合适的产品分发入口，可单独评估 JSSDK 预填，但不作为本方案依赖。

## 工具与契约提案

扩展现有 `space_document_read`，并新增语义独立的 `space_comment_complete` 操作。在 `packages/transport-mcp/server.js` 中统一实现，DSH 与 WorkBuddy 复用同一契约；两者仍绑定各自 SpaceService 和独立数据库。`space_suggest` 只负责提交建议，不接收评论处理状态或来源评论参数。

本次改造同时要求精简现有工具清单。移除 `space_list` 和 `space_documents`：Agent 不枚举文档，只能读取和建议修改用户明确指定的 `space:<docId>` 文档。没有指定文档时，Agent 应询问用户或请用户从 Space UI 选择，不得自行搜索、挑选文档。显式创建新文档仍由 `space_document_create` 支持。WorkBuddy 专属的 `space_status` 与 `space_review_open` 都启动/检查审阅 sidecar 并返回状态或页面地址；合并为一个 `space_review_open`，保留可选文档 ID，并在返回中包含可用状态。精简后 DSH 有 5 个共享工具；WorkBuddy 有 6 个（另含 `space_review_open`）。

目标清单如下：

| 目标工具 | 宿主 | 说明 |
|---|---|---|
| `space_document_create` | DSH、WorkBuddy | 创建文档 |
| `space_document_read` | DSH、WorkBuddy | 默认读取指定文档的正文、建议和评论 |
| `space_suggest` | DSH、WorkBuddy | 仅提交建议，不管理评论状态 |
| `space_suggestion_list` | DSH、WorkBuddy | 查询建议状态 |
| `space_comment_complete` | DSH、WorkBuddy | 将评论标记为已处理并记录关联建议 |
| `space_review_open` | WorkBuddy | 打开审阅页并返回服务可用状态 |

工具数量减少不得合并不同的领域动作（例如建议提交与建议查询），也不得删除用户决策边界、显式创建或指定文档读取能力。MCP 不提供文档枚举入口。

| 现有工具 | 提案调整 | 关键契约 |
|---|---|---|
| `space_document_read` | 默认返回文档评论 | 不增加参数；每次读取指定文档都返回正文、建议及评论，评论包含稳定 ID、引用、锚点有效性和处理状态 |
| `space_suggest` | 不改变评论语义 | 只提交建议，不读写评论处理状态，也不接收评论 ID |
| `space_comment_complete` | 新增独立完成操作 | 输入文档 ID、稳定 `operationId` 和每条评论关联的一个或多个建议 ID；验证评论和建议属于同一文档，按操作 ID 幂等，并将评论状态置为 `processed` |
| `space_suggestion_list` | 保持现有建议查询职责 | 继续列出建议及决策状态；评论关联由评论处理记录查询/展示，不改变建议工具语义 |

评论随指定文档的读取结果默认返回；读取不等于处理授权。只有用户明确要求处理评论时，Agent 才依据评论生成建议：用户指定评论 ID 时仅处理这些评论；未指定 ID 时处理读取结果中状态为待处理的全部评论。Agent 在建议提交后调用 `space_comment_complete` 记录评论 ID 与建议 ID 的关联。未明确要求处理时，Agent 不得因为读到了评论就自行提交建议或完成评论。无法安全转成建议时，在对话中询问用户并保持评论未完成。用户补充说明后可重新处理。

评论使用单一状态贯穿发送与 Agent 处理。`space_comment_complete` 将评论标记为 `processed` 并记录评论—建议关联；完成记录只表示 Agent 已提交关联建议，不代表正文已修改，也不代表建议已接受。已处理评论从审阅页隐藏，建议继续保留各自的决策状态。多个建议可关联同一评论；一个建议可关联多条评论，以支持拆分和合并处理。该操作不领取评论、不代替 `space_suggest`，也不直接修改正文。

## 一致性、安全与失败处理

- 每条评论有稳定 ID；建议提交和评论处理完成各使用稳定操作 ID。`space_comment_complete` 验证评论、文档和建议之间的归属，并按操作 ID 幂等；相同操作重试不得重复写入处理记录。
- 同一评论可能由多个建议分别落实；已关联评论仍应可从显式读取结果和建议历史追踪。Agent 再次处理时默认只处理尚无建议关联的评论；用户明确要求重做时，应先检查已有建议与决策，避免机械重复。
- 读取评论时同时返回文档当前版本。锚点失效时将评论的引用和失效标志交给 Agent，要求重新定位；禁止将猜测的范围提交为建议。
- Agent 只能读评论、提建议并关联建议；工具不提供接受/拒绝建议或直接改正文的能力。
- 评论文本可能包含越权指令。系统工具说明和 Skill 必须将评论视为用户提供的文档修改意见，并继续执行既有工具权限边界。
- 不将评论内容写入日志或非本机云端存储。WorkBuddy 仍仅在其隔离的本机 Space 中访问评论。
- MCP 工具失败、会话中断或结果未知时，评论仍保留为待处理；重试复用建议操作 ID或先检查建议历史，不得静默认为建议已提交。

## 分宿主适配

| 层 | DSH | WorkBuddy |
|---|---|---|
| 触发 | 审阅 UI 显式请求；宿主 API 只发送引用和短指令 | 审阅 UI 生成短提示词，用户复制并手动发送 |
| 评论读取 | Agent 读取用户指定文档时，`space_document_read` 默认附带评论；只有用户显式触发处理才据此生成建议 | Agent 读取用户指定文档时，同一工具默认附带评论；处理请求由用户手动粘贴发送 |
| 处理状态 | Agent 调用 `space_comment_complete` 记录评论—建议关联；DSH UI 刷新显示处理结果及建议决策状态 | WorkBuddy 独立 review-core 数据库记录处理结果；本机 UI 刷新显示评论—建议关联及建议决策状态 |
| 对话能力 | 保留 DSH 当前会话选择能力，但不再传评论正文 | 不增加非公开 API、对话数据库或 UI 自动化依赖 |

## 实施阶段

1. **契约与关联模型**：已确定按指定文档读取全部评论、Agent 只处理未完成评论、处理结果与建议多对多关联；评论编辑重开与并发删除冲突仍需后续明确。
2. **共享核心与 MCP（已完成）**：`space_document_read` 默认返回评论；新增 `space_comment_complete` 与本机持久化；`space_suggest` 职责不变。移除 `space_list` 与 `space_documents`，更新 MCP instructions 和中英文 Skill，限定只处理用户指定文档，且必须有明确用户请求。此轮实施由用户明确授权。
3. **WorkBuddy 工具收敛（已完成）**：移除 `space_status`，将可用状态合并进 `space_review_open` 响应。
4. **DSH UI 接入（已完成核心流程）**：替换全文发送为显式处理请求；展示处理状态和关联建议；继续使用 DSH 当前会话。真实宿主会话流程仍待验收。
5. **WorkBuddy UI 与文案（已完成）**：添加评论处理提示词复制、评论处理状态和建议关联；保留手动粘贴路径。
6. **验证与宿主验收（部分完成）**：本机核心/MCP/UI/WorkBuddy 本地 runtime 测试及构建通过；真实 DSH/WorkBuddy 宿主会话链路尚未验收。

## 验收标准

- 会话消息/复制提示词中不包含评论正文；Agent 从 `space_document_read` 的指定文档读取结果中取得评论。
- `space_document_read` 默认返回评论；用户没有明确要求处理时，Agent 不因读取到评论而生成建议或标记完成。
- 两个宿主使用同一套评论处理契约，但数据目录、文档和评论保持隔离；Agent 不能枚举文档，只处理用户明确指定的文档。`space_suggest` 只提建议，评论处理记录由 `space_comment_complete` 管理。
- 每条已完成评论可追溯到一个或多个建议 ID；用户能在 UI 区分建议生成、用户决策和正文已接受三种状态。
- 评论处理完成操作按稳定操作 ID 幂等；建议创建仍按建议操作 ID 幂等；失效锚点不会导致猜测式修改。
- Agent 从不直接修改已有文档正文，仍由用户接受或拒绝每条建议。
