# 23 · SQLite 底层数据结构升级方案

> 已实现并完成针对性核验。本方案记录从 `markdown-text-v1` / `markdown-text-v2` 升级到 `markdown-text-v3` 的设计与现状；本项目不支持正文版本回溯。

## 目标与边界

升级目标是让 SQLite 自身更好地保证关联数据完整性、限制无效状态，并让主要按文档读取的数据随着记录增长仍能高效查询。现有产品语义保持不变：Markdown 正文保存在 `review_documents`；建议在用户接受前不改正文；评论和发送状态独立持久化；事务和操作 ID 幂等继续有效。

本次不引入历史正文快照、撤销或版本回溯。`review_changes` 只为当前未决建议及评论锚点迁移提供位置映射所需的信息；不把它扩展成可重建正文的事件日志。历史表记录的清理策略需另行定义，不能在本次迁移中猜测依赖关系并删除数据。

## 当前结构观察

当前主要实体为 `review_documents`、`review_suggestions`、`review_operations`、`review_changes`、`space_comments`、`space_comment_sends`、`space_comment_completions`、`space_comment_results` 和协作偏好表。分表边界与业务对象基本匹配。

当前 `doc_id` 关联主要依靠应用代码维护；表定义没有外键和显式二级索引。若干状态、版本和范围字段也没有数据库检查约束。删除文档因此需要在事务中手动清理多个表。评论处理结果中的 `suggestion_ids` 以 JSON 文本保存，适合作为操作结果快照，但不适合作为关系查询入口。

## 目标结构

1. 对确实从属于文档的记录增加数据库级 `doc_id` 外键约束。优先使用 `ON DELETE CASCADE`，由文档删除事务统一清理派生记录；删除前仍保留“发送进行中时拒绝删除”的业务检查。外键必须在每个 SQLite 连接上启用，并在迁移和启动时验证。
2. 为常用访问路径建立索引，至少评估：
   - `review_suggestions(doc_id, status, created_order)`：读取活动建议并按创建顺序展示。
   - `review_suggestions(doc_id, created_order)`：读取完整建议历史。
   - `space_comments(doc_id, status)`：读取文档评论及发送/编辑状态检查。
   - `space_comment_sends(doc_id, status)`、`space_comment_completions(doc_id)`、`space_comment_results(doc_id)`：按文档清理或读取处理状态。
   - `review_changes(doc_id, version)` 已由主键覆盖，不重复创建等价索引。
   索引以真实查询计划为准，避免重复索引增加写入成本。
3. 为有限枚举添加 `CHECK` 约束：建议状态为 `pending`、`accepted`、`rejected`、`conflicted`；评论状态覆盖当前实际状态 `pending`、`sending`、`sent`、`failed`、`unknown`、`processed`。发送记录状态覆盖 `sending`、`sent`、`failed`、`unknown`。迁移前必须以代码和现存数据库数据确认枚举全集。
4. 对可明确表达且兼容现有合法数据的数值字段添加非负、范围及单点主键约束，例如版本号与坐标非负、`to_pos >= from_pos`、`inserted_length >= 0`。UTF-16 代理对边界和坐标必须匹配正文等语义校验仍由应用层负责。
5. 暂不把 `space_comment_results.suggestion_ids` 拆成关系表。它当前用于保存处理结果快照，且删除文档时整体删除；若后续出现按建议反查评论的产品需求，再单独设计规范化关联表。

## 版本与模块边界

目标审阅 schema 标记为 `markdown-text-v3`，数据布局标记为 3。前者描述审阅表结构，后者描述同一数据目录中跨模块的总体布局兼容性。

历史数据迁移放在 `packages/review-core/src/migrations/index.js` 独立模块中。迁移器负责识别源版本、校验前置条件、建立并核验 `.pre-v3.bak` 副本、迁移表与索引、更新 schema 标记并核验结果；`review-core.js`、`comments.js` 和 `collaboration-store.js` 只调用迁移入口，不包含旧版本补列、建表或旧库导入分支。

后续可按迁移器覆盖范围逐步删除过期兼容逻辑：先迁移旧格式并确认仍受支持版本已覆盖，再移除分散在建表逻辑中的列补齐、旧表清理和旧 schema 兼容分支。每次删除兼容逻辑都须由版本支持策略和真实用户数据版本分布支撑，不以“迁移代码已存在”作为唯一依据。

## 迁移步骤

1. **盘点和预检**：独立迁移模块读取 schema 标记和实际表结构；确认来源为明确支持的 v1/v2；检查孤儿 `doc_id`、未知状态、负版本/坐标、`to_pos < from_pos`、重复文档内创建顺序及主键冲突。未知 schema 或校验失败时停止，不自动清库、不静默改值。
2. **准备可恢复副本**：迁移开始前用 SQLite `VACUUM INTO` 创建 `<database>.pre-v3.bak`，并核对完整性及文档、建议、评论行数。副本无法验证时停止迁移；原库事务仍可回滚。
3. **事务化升级**：在一个受控写事务中重建需要新增外键或检查约束的表，复制并验证数据，创建索引，运行外键检查，再更新 `markdown-text-v3` 标记。SQLite DDL 和数据复制失败均回滚；需要留存迁移阶段信息时使用独立迁移记录表，避免只依赖代码版本推断。
4. **升级后核验**：检查目标表定义、行数和关键字段摘要；运行 `PRAGMA foreign_key_check` 与 `PRAGMA integrity_check`；核对所有旧未决建议、评论、发送状态和操作结果仍在且关联有效。
5. **运行时切换**：迁移完成并核验后，所有新写入经目标 schema 和外键约束。若数据库已标记 v3 但当前程序不支持 v3，启动必须失败并保留数据，不能由旧程序降级打开。
6. **逐步移除兼容代码**：后续版本在确认目标支持窗口后，逐项删除迁移完成的旧列补齐/旧格式兼容代码。迁移模块可以保留已发布来源版本的升级路径，或在支持窗口结束后整体移除；保留窗口和移除条件应记录在 release 说明中。

## 回滚与失败处理

迁移事务提交前的错误由 SQLite 回滚。提交后若新版本运行失败，使用迁移前的已验证副本恢复；不可让旧版本直接打开并改写 v3 数据库。恢复流程必须保留迁移期间新产生的数据或明确限定在首次启动切换窗口内执行，不能把旧副本覆盖到已接受新写入的数据库。

孤儿记录、未知枚举或不合法坐标意味着现有数据与应用假设不一致。迁移应报告具体表、记录 ID 和原因，并保留原库供修复；不自动删除记录或重猜锚点。数据修复如需改变用户内容或建议决策，须走单独的显式方案。

## 实施验收结果

- 从每个仍受支持的旧 schema 版本迁移到 v3，迁移重复执行安全，失败可恢复，未知版本安全停止。
- 对已有数据验证行数、主键、文档内容、建议状态、评论锚点、发送/处理结果及幂等操作记录一致。
- 外键打开后，跨文档引用和孤儿写入被拒绝；文档删除的业务检查仍阻止删除正在发送的评论，并能原子清除从属数据。
- 检查约束拒绝无效状态和非法范围，合法的空插入范围仍允许。
- 验证目标查询使用预期索引，索引没有重复覆盖；文档列表和按文档读取结果不变。
- 多连接并发、写事务中断及重启后数据库保持一致；`PRAGMA foreign_key_check` 和 `PRAGMA integrity_check` 通过。
- 不增加版本回溯能力；不以 `review_changes` 重建旧正文，也不承诺从其恢复历史文档内容。

针对性核验已覆盖 v1/v2 到 v3、旧评论处理记录保留、旧协作库一次性导入、并发启动、外键及状态约束、查询索引、备份完整性和未知 schema 失败关闭。完整仓库检查结果以本次实现记录为准。

## 相关规范

迁移实现已更新 [07](07-review-core.md)；当前 Desktop 的数据布局检查使用版本 3。后续 schema 升级应在独立迁移模块追加明确版本迁移，并在移除旧来源支持前确认数据升级路径仍覆盖支持范围。
