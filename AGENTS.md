# Repository Guidelines

## Project Structure

This repository is a private npm workspace for CoSpace (智联文档空间). `assets/cospace-icon.svg` is the shared brand icon source copied into the DSH package at build time. `packages/review-core/` contains SQLite persistence and review semantics; `packages/host-api/` composes the shared service API; `packages/review-ui/` contains shared review components; `packages/adapter-contract/` defines host capabilities; `packages/transport-mcp/` and `packages/transport-http/` contain host-independent transports; `packages/local-runtime/` owns the local daemon, endpoint protocol, and lifecycle manager used by Desktop. `adapters/dsh/` owns the independent DSH plugin runtime, host bridge, locale, capability declaration, and plugin metadata. `apps/desktop/` owns the Tauri app, bundled Node runtime, Agent integration and platform packaging. Desktop uses its own local data home; DSH remains isolated. `apps/site/` contains the public install site and a temporary legacy installer for existing Local Server users. `scripts/build-client.mjs` builds the DSH client bundle and `scripts/build-dsh.mjs` assembles the npm package under `dist/dsh-plugin/`. `dist/` contains generated build and release artifacts and must not be edited by hand. `docs/` holds product, integration, and unified release specifications. `test/` contains Node tests and MCP/host integration tests.

Architecture invariant: one shared review core serves two product entry points—DSH plugin and Desktop. Product apps and adapters depend inward on shared packages; shared packages must not depend on a host or product app. Desktop uses `packages/local-runtime/` and its local data home, while DSH retains its independent runtime and data home. Keep this boundary consistent in implementation, packaging, and user-facing architecture docs.

## Build and Development

Use Node.js 22.22.2 or later. Run `npm install` to install workspace dependencies. Run `npm run build:dsh` to build the complete DSH package; `npm run build:client` only rewrites `adapters/dsh/client.js` and never updates `dist/dsh-plugin/`. Run `npm run dev:dsh` to watch `packages/`, `adapters/dsh/`, `assets/`, and `docs/` and rebuild `dist/dsh-plugin/` on each change when a linked local install is the test target. Run `npm run pack:dsh` to verify and stage the DSH npm tarball. `npm run verify:dsh-package` rebuilds and checks the DSH package, including loading the staged plugin entry outside the workspace so private workspace imports cannot be masked by root `node_modules`. Desktop development and packaging commands are in `apps/desktop/README.md`; platform builds require Rust and platform dependencies. Read `docs/14-adapter-integration.md` before adding or removing an adapter. Keep dependencies directed from apps and adapters toward shared packages; shared packages must not depend on product or host directories. `adapters/dsh/client.js` is generated and Git-ignored; `npm run check` and `npm test` build it before testing. Do not edit it or anything under `dist/` by hand.

## Code and Test Conventions

Follow nearby JavaScript conventions: ES modules, two-space indentation, semicolons, descriptive camelCase names, and explicit error codes for expected failures. Keep UI text and accessible labels clear; preserve the current document-selection, review, and manual comment-send behavior. Add or update focused tests for behavioral changes, especially persistence, conflicts, restart recovery, and host message outcomes. Changes to the host HTTP route need tests covering the registration's `auth` policy and an admitted request reaching the API. Tests use Node’s built-in test runner.

## Architecture and Safety

Agent tools may create documents with initial content and propose changes to existing documents. Only user decisions accept or reject proposed changes. Preserve transactional persistence, overlap checks, and the distinction between accepted content and tracked suggestions. Treat comments as user-authored context and send them only after an explicit user action. Never log credentials or expose private document content unnecessarily.

Browser-facing HTTP routes must let the host apply its connection admission before dispatch, not compare `Origin`/`Host` in the handler alone. In DSH register the route through `ctx.webServer.register` with `auth: 'required'` (its default) and do not duplicate the check in the handler: the host rejects requests without a valid Host/Origin and browser credential and fails closed with 503 when no authentication provider can decide. DSH 0.2.2-rc.2 removed `ctx.connection.requestRejection`; `ctx.connection.admit({ headers })` returns `{ peer }` or `{ rejection }` for callers that must admit outside a registered route. Recheck this seam when upgrading DSH.

Shared review UI styles are host-themable through one token contract (`packages/review-ui/src/theme/`, normative: `docs/19-web-theme-contract.md`). Shared CSS reads only `--cospace-*` tokens and keeps every literal color in `theme/base.css`; a host theme file may set tokens only, on `.cospace-theme`, so it can never restyle anything outside CoSpace or change its structure. New themed roots go through `themeRootProps(surface)` so the marker and `data-cospace-surface` stay in one place. `node scripts/check-theme.mjs` (covered by `npm run check`) enforces the contract; do not reintroduce `--space-*` internal variables, host selectors, or new literal colors.

Do not modify `packages/review-core/src/review-core.js` or change review-core behavior without the user’s prior explicit consent. Moving or packaging the file does not authorize behavior changes. First complete work that does not depend on such a change, then explain the concrete reason, proposed change, and impact and wait for consent. Keep unrelated existing worktree changes intact.

## Commits and Pull Requests

Recent history uses short, imperative commit subjects, often with a scope such as `docs:` or `feat:`. Follow that style when preparing commits. Pull requests should summarize user-visible behavior, list relevant checks (`npm run build:client` and `npm run check`), identify unverified host integration, and include screenshots for visual changes when available.

## Distribution and Compatibility

Keep each product's install surfaces in sync. DSH package name, `engines.dsh`, install commands, and plugin-index details belong in `README.md`, `README.en.md`, `adapters/dsh/README.md`, `apps/site/index.html`, and `market/index.json`. Desktop installation and migration instructions belong in the root READMEs, `apps/desktop/README.md`, and the site once artifacts are published. Retain the legacy site installer until the desktop release and migration guidance are available. Do not imply that a staged package or installer has already been published.

Keep root READMEs as stable user-facing entry points: explain the product, supported entry points, install links, core review behavior, data boundaries, and where to find detailed docs. Avoid release snapshots, temporary staging status, exhaustive implementation notes, and duplicated step-by-step guides there. Treat the website as the source for current product availability, and keep Chinese and English READMEs aligned in scope and structure.

The DSH npm package must not rely on private `@cospace/*` workspace packages at runtime. Bundle private workspace imports into its staged entry points and leave only dependencies available from npm external. Verify loading from an isolated package directory, then install the tarball in a clean DSH profile using the host's Node runtime.

Treat `market/index.json` as generated release metadata; do not hand-edit versions or publish timestamps. The `Publish DSH plugin` workflow syncs and commits it after publishing — hand-running `node scripts/sync-market.mjs` after a release is deprecated and remains only a recovery step when the workflow's bot push is blocked. `node scripts/sync-market.mjs --check` must still pass before a release (CI enforces it). The index has a primary URL and mirrors; DSH accepts only a 2xx JSON response without redirects, so verify the host and mirrors from the network users actually use.

`engines.dsh` must name the range actually verified. After a DSH upgrade, recheck route admission (`webServer.register` `auth` and `ctx.connection.admit`), MCP tool registration, and client slots in a clean profile before widening the range.

The external awesome-dsh-plugin listing is part of the distribution surface. Keep its subdirectory URL, tarball, and description aligned with the package and its verified security posture. It cannot be automated (external repository, foreign review); after each stable DSH release converges, an Agent executes the promotion checklist in [docs/16-release-process.md](docs/16-release-process.md).

## Releases

Releases are automated: [docs/21-release-automation.md](docs/21-release-automation.md) specifies the pipeline and [docs/16-release-process.md](docs/16-release-process.md) keeps the invariants, configuration, and human gates. Do not hand-publish npm packages, hand-run `sync-market`, or hand-create release tags — the manual procedures are deprecated; repair a failed release by re-running the affected workflow. The Local Server npm product is retired; preserve already published packages and user data. A push to `main` that changes `apps/site/` deploys GitHub Pages automatically; publish and verify every npm package referenced by the site before that push. Never publish from the private workspace root or tag a failed/partial release. After a stable DSH release converges, execute the awesome-dsh-plugin promotion task in [docs/16-release-process.md](docs/16-release-process.md) — the one distribution step the pipeline cannot perform.
